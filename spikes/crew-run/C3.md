Local check instead (release build, `--base-href /flutter-kiro-skeleton/`, served under `/flutter-kiro-skeleton/`, headless Chrome with SwiftShader, viewed at 900 px wide). Of the 10 articles, `Image.network` and `CachedNetworkImage` gave the same result per host. `assets.science.nasa.gov` (3 articles) loaded with both loaders. `spacepolicyonline.com` (2), `www.nasaspaceflight.com` and `images-assets.nasa.gov` failed with both loaders, and each error widget named its loader. `www.nasa.gov` was blank in both columns at capture time (no error shown, so probably still loading). `cdn.arstechnica.net` (2) loaded with `Image.network`. Rounded corners (radius 8) and the 0.5 px border showed on every cell, including the images that loaded. The failures are probably CORS or hotlink blocking by the image hosts; I did not check the cause. A CORS block on `Image.network` is expected in CanvasKit, so a pass here does not show that Pages behaves the same. Decision: plan kept for the app-side pattern. Not decided for the image hosts: some article images will not load on web, so Phase 5 needs a fallback (a proxy, or accepting the error widget). Repeat on Pages once billing is fixed; repeat on an iPhone too.
  - S24: Not verified on GitHub Pages (same failed run). Local check: `/flutter-kiro-skeleton/a/b` opened directly renders the "Deep link /a/b works" page when the server returns `404.html` (a copy of `index.html`) with status 404 for unknown paths. That is the behaviour Pages has. `python3 -m http.server` does NOT do this: it returned a plain 404 for `/a/b`, and the screenshot was blank. So I used a small custom server in `/tmp` that serves `404.html` on 404, which models Pages but is not Pages. Reload on `/a/b` was not tested separately (the direct open is the same request). Decision: plan kept (`usePathUrlStrategy` + `404.html` copy), pending a Pages check.
